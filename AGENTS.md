# AGENTS.md

Instructions for any agent (Claude Code, Codex, Cursor, ...) writing or editing content in this repo.
Read it before touching a tutorial or challenge, and run the checklist before every push.

## What this repo is

The source for Shiv's [iximiuz Labs](https://labs.iximiuz.com/a/shiva-swaroop) tutorials and challenges.
`README.md` has the layout. The short version:

- `tutorials/<slug>/` and `challenges/<slug>/` are published exactly as they are by
  `dev/push.py <kinds>/<slug>` (a safe wrapper around `labctl content push`). The folder name is the Labs name,
  hash suffix included.
- `dev/`, `tools/` and `docs/` never get published. Learners will never see them.

## The one rule behind most review comments

**The learner only sees the page and the playground.** They don't see this repo, its scripts, its
history or this conversation. That means:

- The page, the task hints and every shipped file (anything in `__static__/`, plus every folder
  packed into `__static__/<folder>.tar.gz`) must never mention `dev/`, `tools/`, `render.py`,
  `lint.py`, run-tests, harnesses, templates, `.labctlignore`, `.solution.sh` or this repo.
  This also covers code comments inside shipped files. A comment like "Generated by dev/render.py"
  in a shipped YAML is exactly what a reviewer flagged once.
- If a shipped file was generated, say where its content comes from in learner terms
  ("Same as ~/pet-crd/1-names.yaml in that tutorial's playground"), not how this repo makes it.
- Every path the page names (`~/pet-operator/config/...`) has to exist in the playground once
  startup finishes. Every command the page shows has to work there.
- `solution.md` and `.solution.sh` are fine: Labs only shows them to the author. `__static__/` is
  public and served from a CDN, so nothing private goes in there.

## Playground setup

- Ship code as folders next to `index.md`, listed in `startupFiles` as
  `source: __static__/<folder>.tar.gz` with `extract: true` and `owner: laborant`. List the folder in
  the content's `.labctlignore` so push doesn't upload its raw files too. Each shipped folder gets
  its own `.labctlignore` with at least `.DS_Store`.
- **Point the IDE at the project.** When the learner works in one shipped folder, add:

  ```yaml
  - path: /etc/default/code-server
    content: |
      CODE_SERVER_PATH=/home/laborant/<folder>
    owner: root
    mode: "644"
    machines: [<the machine the learner works on>]
  ```

  Without this, the IDE opens `~`.
- Every `startupFiles` entry that isn't extracted needs `append: true`, or both `owner` and `mode`.
  There are at most 20 entries.
- Never put a `.md` file in `__static__/`. Labs parses it as content and rejects the push.
  Rename it to `.txt` and unpack it under a `.md` name with `startupFiles` if you need to.
- Init tasks run as root unless `user:` says otherwise. Anything written into `/home/laborant` needs
  `user: laborant` or `owner: laborant`.

## Page conventions

- **Cover:** a tutorial uses one of its own diagrams as `cover:`, usually the opening
  overview diagram. Don't use a generic or generated-looking `cover.png`. Challenges keep their `cover.png`.
- Diagrams come from `tools/diagrams/` (see its README for the style: Nunito for the names of things,
  hand-lettering only for notes). Rebuild the PNGs with `npm run build` there, then embed them from
  `__static__/`.
- Bump `updatedAt` whenever you change a published page.
- Voice: Shiv's own, first person, plain. Run the `de-ai` skill on any prose before it ships.
- Show real output captured from the real environment (k8s-omni or a kind cluster on the same
  Kubernetes version), never output written by hand.
- Use wording that matches what actually happened. For example, `--dry-run` results "would get in",
  they don't "get in". When a reviewer suggests exact wording, use it verbatim.

## Tutorials are rendered, not edited

`tutorials/*/index.md` is generated from `dev/<name>/tutorial.template.md` by `dev/render.py`,
which quotes the shipped files through `{{file:...}}` / `{{excerpt:...}}` directives. Edit the
template or the shipped file, then run `dev/render.py`. Never hand-edit a rendered `index.md`,
because the next render overwrites it. The `pet-operator/config/crd-*.yaml` copies are generated
from the zoo tutorial's `pet-crd/`, so edit those files instead.

Challenges have no template, so edit `challenges/<slug>/index.md` directly.

## Checklist before every push

Run all of these, in order. Don't push if any of them fails.

1. `dev/render.py` (when a tutorial changed). It runs the lint below on what it is about to write.
2. `dev/lint.py` (all folders) or `dev/lint.py <kinds>/<slug>`. It checks:
   - repo-only references and leftover TODO or `{{directive}}` text in the page, `__static__/` and every
     shipped folder (packed with labctl's own ignore rules);
   - that the cover exists, and that a tutorial's cover is one of its diagrams;
   - that every embedded image exists;
   - `startupFiles` push rules, archive folders and their `.labctlignore`, and the
     `/etc/default/code-server` entry when one project is shipped;
   - `bash -n` on every task `run` and `hintcheck`;
   - that `updatedAt` isn't before `createdAt`.

   If a new review comment points at a mistake a script could catch, add the check to `dev/lint.py`
   and a line to this file, in the same change.
3. The harness for any tutorial you touched, against a disposable cluster
   (`kind create cluster --name iximiuz-test --kubeconfig /tmp/kc && KUBECONFIG=/tmp/kc dev/<name>/run-tests.sh`).
   For a challenge, run `.solution.sh` on a fresh play and check that every task flips to completed.
4. Read the page once as a learner: open the rendered `index.md` and each shipped file, and ask
   "could I follow this with only the playground in front of me?"
5. Push with **`dev/push.py <kinds>/<slug>`**, never a bare `labctl content push`. `labctl` is
   already authenticated on this machine. `push.py` lints, packs every `__static__/<folder>.tar.gz`
   from its folder, pushes with `--force`, then pulls the content back and fails unless Labs matches
   the repo byte for byte. A bare `labctl content push --force` (0.1.107) deletes the remote archives,
   which are gitignored locally, and uploads nothing in their place, so the playground starts empty.
6. Verify the playground on Labs whenever startup files or init tasks changed. Start the content
   (MCP `start_content`, or the page) and check the result in the play itself, for example
   `cat /etc/default/code-server` and `ls -la ~/<folder>`. Then destroy the play.
7. Commit and open a PR the way the history does: one PR per round of feedback, with a message that
   lists each change and how it was tested.

## Past review feedback, kept so it doesn't come back

- Repo tooling (`dev/render.py`) was named in a shipped file's comment header (lint rule 1).
- A tutorial's cover was a generic image instead of one of its diagrams (lint rule 2).
- The IDE opened `~` instead of the shipped project (lint rule 4).
- `--dry-run` results were described as if the objects were stored (wording, see above).
- Diagram text used hand-lettering for the names of things (diagram style, `tools/diagrams/README.md`).
- A hint script had a bash syntax error from an unescaped apostrophe (lint rule 5).
- A bare `labctl content push --force` deleted the shipped `pet-operator.tar.gz` from Labs (use `dev/push.py`).
